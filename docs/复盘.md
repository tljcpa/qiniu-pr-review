### D-01: 后端框架（FastAPI vs Flask vs Django）
- 选项：A FastAPI（async+Pydantic）/ B Flask（轻量）/ C Django（重）
- 选 A。理由：LLM 流式调用(SSE)与多 provider 并发交叉验证都需要 async；Pydantic 直接当结构化 finding 的 schema 用，省一层手写校验；自带 OpenAPI 文档对评委友好
- 不选 B：Flask 上 async 是补丁，流式/并发体验差
- 不选 C：Django 全家桶对一个 3 天单体工具是负重
- 改变条件：若要兼容 Python 3.7 老环境或团队只熟 Flask

### D-02: 前端方案（React+Vite vs Next.js vs 纯 HTML）

- 不选 B：Next.js 的 SSR/路由/server 组件对一个单页工具是负重,还要跑 node 运行时
- 不选 C：手撸状态管理(进度流 + 多 finding 展开折叠)会很乱

### D-03: 数据库选择（SQLite vs Postgres vs 仅内存）

- 选 A(本期)。理由：演示场景无需持久化结果;缓存(D-09)和 job 状态都进程内够用;少一个依赖、部署更简单

### D-19: SSE 流式 + 后台任务 + emit 回调（API 设计）
- 目标：演示时粘贴 URL 后能实时看到"拉取->分层->扫描->逐条深读->出结论"的进度,而非干等十几秒黑屏
- 决策：
  - POST /api/review 立即返回 review_id 并起后台 asyncio 任务;GET /api/review/{id}/stream 是 SSE(原生 EventSource 兼容);GET /api/review/{id} 返回最终 JSON
  - router/service 同步实现(D-04b)不改,加一个可选 emit(event) 回调贯穿各阶段;后台任务用 run_in_threadpool 跑同步 review,emit 通过 loop.call_soon_threadsafe 把事件塞进 asyncio.Queue,SSE 端从 queue 取
  - 为什么不把整条链路改 async:LLM 调用是同步 SDK,改 async 收益小、风险大;线程池 + 线程安全 queue 已满足流式
  - 为什么用 emit 回调而非把 router 改成 generator:回调是附加的、不破坏已冻结的 review() 返回契约,单测里收集 events 到 list 即可验证
- 为什么 POST+GET 分离而非单 GET SSE:EventSource 只能 GET,但 URL 当 query param 要编码且不洁;POST 建任务拿 id 再开流更清晰
- 改变条件：要 token 级实时思维链(逐字蹦)再把 reasoner 调用改 async streaming

### D-04: LLM 调用方式（OpenAI SDK vs 直接 HTTP vs LangChain）
- 选项：A openai-python SDK / B 手写 httpx 直连 / C LangChain
- 选 A。DeepSeek 与 Azure 都兼容/原生 OpenAI 协议，一套 SDK 通吃；SDK 自带类型、错误分类(RateLimitError/APITimeoutError 等)，退避好写
- 不选 B：要自己处理重试/错误分类/SSE 解析，重复造轮子
- 不选 C：套壳、隐藏 prompt 与 token 细节，与"自写核心链路显功底"目标冲突
- 自封一层 LLMProvider 抽象：屏蔽 DeepSeek/Azure 差异，统一返回 content + reasoning_content + usage，便于路由层与交叉验证调用
- 改变条件：要接非 OpenAI 协议模型（如本地 vLLM 特殊接口）时在抽象层加 adapter

### D-04b: LLM 调用先同步后异步（避免过早复杂化）
- 决策：PR3 的 provider 用同步 openai client（complete 请求/响应式）
- 理由：chat 快扫 / reasoner 深读 / 交叉验证都是请求-响应，FastAPI 里用 run_in_threadpool 即可不阻塞事件循环；PR9 的 SSE 流式是"按 finding 完成度推送进度"，不依赖 token 级流式
- 为什么不一上来全 async：async client + 流式 reasoning 解析会让 PR3 变大、违反"一个 PR 一件事"，且收益要到 PR9 才显现
- 改变条件：若要做 token 级实时思维链流式，再在抽象层加 async complete_stream

### D-05: 上下文工程的层次划分（L1-L4 的具体边界）
- 问题：长 PR 不能整个 diff + 全仓库塞进 prompt，会爆 context 也烧钱；但只给 diff 又缺上下文导致误报
- 决策：按"改动规模"分四层，受一个可配 token 预算（默认 24k，留给输出）动态裁剪
  - L1 (总是)：PR 标题/描述 + 改动文件清单 + 每文件增删行数
  - L2 (小, 改动总行 < 800)：每个改动文件的完整内容
  - L3 (中, 800~3000)：改动 hunk + 所在函数/类全文 + 该文件 import + 同文件其他函数签名
  - L4 (大, > 3000)：仅 hunk + 跨文件引用（grep 改动符号在 repo 其他位置），并**主动声明本段未完整 review**
- 为什么不做语义向量检索：3 天内 embedding+建库收益不稳，分层启发式足够且可解释
- 改变条件：若接入 sqlite-vec 做相似函数召回，可在 L3/L4 间加一层语义层
- 注：阈值是初值，PR5 用真实 PR 实测后调，调整记到本条下方

### D-06: 模型路由策略（哪个模型在哪个阶段调用）
- 决策：三段式路由（直接命中题目"模型选择设计思路"评分点）
  - 第一遍 deepseek-chat：全上下文快扫，产出"可疑片段"候选清单（便宜、快）
  - 第二遍 deepseek-reasoner：只对可疑片段深读，**保留 reasoning_content 思维链**（可解释性亮点）
  - 第三遍 gpt-4.1-mini：仅对 high 严重度 finding 交叉验证，同结论=high 置信，异结论=降级 medium
- 为什么不全程上 reasoner：reasoner 贵且慢，对明显无风险代码是浪费；先 chat 过滤再深读，成本/质量平衡
- 为什么交叉验证只给 high：Azure 配额 10k TPM 有限，省在刀刃上；low/medium 误报代价低
- 改变条件：余额/配额充足时可对 medium 也交叉验证；或全部上 reasoner 提质

### D-07: 风险代码识别的 prompt 设计（如何避免误报）
- 决策：system prompt 明确"资深评审"角色 + 三条抑制误报规则
  1. 只报具体、可操作的问题；不为风格吹毛求疵(除非引发 bug)
  2. 拿不准就标 low confidence，不要硬报
  3. 要求每条 finding 给 file/行号线索/严重度/类别/建议，强制结构化逼模型落到实处而非空泛
- 输出强制 JSON：用 response_format 或 prompt 约束，便于解析与去重
- reasoner 深读阶段反向施压：要求它对每条候选给 confirmed/false_positive 裁决，假阳性直接降级——这是误报控制主力
- 为什么不让 chat 一遍定稿：chat 召回高但精度一般，留给 reasoner 把关精度
- 改变条件：误报实测偏高就加 few-shot 负例；偏低(漏报)就放宽 chat 温度

### D-16: 路由的两段编排与 reasoner 调用粒度
- 决策：chat 扫一次出候选清单；reasoner 对每条候选单独调一次(而非批量一次)
- 为什么单条调用：reasoning_content 是按"整次 completion"返回的，批量则多条 finding 共享一段思维链，无法在 UI 上逐条展开；单条调用 = 每条 finding 一段独立思维链(亮点3的数据结构基础)
- 代价：N 条候选 = N 次 reasoner 调用，慢且贵。但用户已给 5x 额度可激进；且只对候选(通常个位数)深读，不是对全文
- 防爆：max_deep_read 上限(默认 12)，超出的候选保留 chat 结论但标记"未经 reasoner 深读"
- 改变条件：要压成本就改批量(牺牲逐条思维链)；要更快就并发调用 reasoner

### D-17: 路由产出 RawReview(dataclass)，PR7 再转 Pydantic
- 决策：router 产出内部 RawFinding/RawReview(dataclass)，PR7 的 Finding/ReviewReport(Pydantic)消费它做置信度评分+去重+序列化
- 理由：单向依赖，router 专注"调模型拿原始判断"，PR7 专注"打分/聚合/对外契约"，各做一件事不互相回改
- 这是接口冻结点：RawFinding 字段定了，PR7/PR8/PR9 都按它来

### D-08: 置信度评分公式（如何打分）
- 目标：给每条 finding 一个 high/medium/low，让 UI 折叠 low、突出 high，回答"误报控制"
- 信号(0~1 加权求和，详见 finding.py)：
  - verdict 权重最大：confirmed=+0.5, uncertain=+0.1, unverified(超 deep_read 上限)=+0.0
  - 是否经 reasoner 深读：deep_read=+0.15
  - 思维链充分度：reasoning 长度映射到 0~0.2(越长越说明推理充分，封顶防灌水)
  - 交叉验证(PR12 填)：cross_agree=+0.15, cross_disagree=-0.2
  - 严重度自评：high=+0.1, medium=+0.05, low=0（严重度高的略加，但不主导）
- 分档：score>=0.65 -> high, >=0.35 -> medium, else low
- 为什么 verdict 主导：reasoner 的核实结论比模型一开始的自评更可信
- 为什么思维链长度只给 0.2 且封顶：长度是"推理充分"的弱信号，不能让模型靠啰嗦刷高分
- 改变条件：实测 high 里误报多就提高阈值或降 verdict 权重；接入交叉验证后重新标定

### D-18: 去重策略（同一问题被多次报告）
- 决策：按 (规范化file + category + 规范化line_hint) 去重，保留置信度更高的一条
- 为什么用"位置"而非"标题"：初版用标题前 12 字做 key，单测即暴露问题——模型对同一问题的标题措辞差异大(如"空指针风险" vs "空指针风险在这里"前缀只共享 5 字)，按标题会漏合并。位置(文件+类别+定位)才是同一问题的稳健信号
- 规范化：file 去空白小写；line_hint 去掉所有空白再小写
- 为什么不做语义去重：3 天内 embedding 去重收益不稳；启发式够用且可解释
- 改变条件：误合并(不同问题同位置被并掉)增多就把 category 细化或加标题辅助；漏合并就放宽
- 教训：去重 key 选"措辞"必然脆，选"位置/身份"才稳——单测帮我在写代码 5 分钟内就发现了这个设计缺陷

### D-09: 缓存策略（key 怎么定、何时失效）
- 决策：两级缓存，进程内 dict（BRIEF 明确不引 Redis）
  - 一级 文件 diff 哈希：key = sha1(filename + "\n" + patch)。这是"增量 review"的原子单位——同一文件 diff 没变就复用其 findings
  - 二级 整报告：key = sha1(head_sha + 所有文件 diff 哈希拼接)。同一 PR 没新 push -> 整份报告秒回（演示体感顺）
- 失效：天然内容寻址——patch 变了哈希就变，旧条目自然不命中，无需手动失效；进程重启即清空（演示足够，不需要持久化）
- 增量：对比两次的文件 diff 哈希集合，只对新增/变化的文件调模型，命中的复用
- 为什么不持久化到 SQLite：演示场景进程内够用；BRIEF 也说缓存不必要重依赖。留作扩展
- 为什么不按 start_line/end_line 拆更细：行级缓存对"函数级 review"收益小且复杂；文件级 diff 哈希粒度刚好
- 改变条件：要跨进程/重启保留就加 SQLite 后端（接口已留 get/put 抽象）

### D-27: 安全修复 —— CORS 非法配置 + 公开端点限流（安全审计必修）
- 背景：独立安全复核发现两处硬伤，临期最小化修复
- ① CORS：`allow_origins=["*"]` 叠加 `allow_credentials=True` 会反射任意 Origin（非法配置，浏览器侧等于放开跨站带凭证）
  - 修：本项目无 Cookie/凭证鉴权，根本解是 `allow_credentials=False`；同时默认 CORS 白名单收紧为线上域 + 本地开发域（双保险）
  - 为什么不只留白名单：关 credentials 是根因解，白名单是纵深防御，两者都做且改动极小
- ② 公开 `POST /api/review` 无鉴权无限流 + DeepSeek 仅 ¥11：demo 当天可能被刷爆烧光、站点挂
  - 修：自写进程内滑动窗口 IP 限流（默认每 IP 60s 内 10 次，超限 429），不引 slowapi（少依赖）
  - 经 Caddy 反代，真实 IP 在 `X-Forwarded-For` 首段，不能用 request.client.host（那是 127.0.0.1）
  - 限额入 config 可调；防刷够用即可，不做分布式/令牌桶等过度工程
- 改变条件：要精确限流/多实例再上 Redis + 令牌桶；有真实用户鉴权再引入 API key

### D-28: 用自己的工具自审自己的代码（dogfooding）
- 动机：本项目代码几乎全由 AI 写，拿我们做的 review 工具审最易藏 bug 的自己 PR #9(API+SSE+asyncio+线程)——既验证工具实用性，又找真问题，也是答辩强叙事
- 结果：工具报 5 条，且对 HIGH 那条做了交叉验证 agree。人工逐条分流(不盲修)：
  - [1] HIGH 多 SSE 连接共享一个 Queue 会错乱：**真实并发缺陷**。但触发需"同一 review_id 开多个流"，我们前端每次 POST 生成新 id 只开一个流，正常 demo 不触发；临期重写 SSE 风险>收益 → 记为已知限制不动
  - [2] MEDIUM _jobs 内存泄漏：**已在 PR #17 修过**(有界 LRU)。模型审的是 PR #9 旧快照看不到后续修复 → 不重复修（恰好印证"增量 review 看的是 PR 当时状态"）
  - [3] MEDIUM 客户端断开后台任务不取消：真实，但断开的 review 仍写缓存非纯浪费，且有限流+job 上限兜底 → 记为已知限制
  - [4] LOW 心跳 30s 偏长：一行改 15s，零风险 → 修
  - [5] LOW emit 空函数 3 处重复：提取 app/core/events.py noop_emit → 修
- 价值：工具在自己 AI 写的代码里找出真实 HIGH 并发 bug 并被交叉验证确认；人工判断分流(修2/已修1/已知限制2)正是"不黑盒"。已知限制写进 FUTURE_WORK
- 改变条件：[1][3] 若要支持多端同看同一 review，需把 Queue 改成 per-connection 广播 + 后台任务可取消

### D-12: GitHub 拉取的边界处理（大 PR / patch 缺失 / 文件全文）
- 问题：大 PR 文件多、单文件 diff 可能巨大；GitHub 对 files 列表有上限（3000 文件），单文件 >～20万行或二进制时 `patch` 字段为 None
- 决策：
  - files 用 PaginatedList 迭代但设 `max_files`（默认 300）上限，超出则截断并在结果里标 `files_truncated=True`，不静默丢
  - patch 为 None（二进制/超大）时保留文件条目（含增删行数），patch 置 None，上层据此降级到只看文件名
  - 文件全文拉取（get_contents）单独方法、按需调用：>1MB 文件 PyGithub 解码会抛，catch 后返回 None 标记拿不到，不让整次 review 崩
- 为什么不一次性拉所有文件全文：浪费 API 配额且大多数文件 L1/diff 就够；全文留给 PR5 上下文构建按层级按需拉
- 改变条件：接入仓库本地 clone 模式后，全文从本地读，不走 API

### D-14: token 估计用确定性启发式而非 tiktoken
- 选项：A 自写启发式(ASCII~4字符/token, CJK~1.5字符/token) / B 引入 tiktoken / C 调 API 数 token
- 选 A。理由：DeepSeek 不是 OpenAI tokenizer,tiktoken 对它本就不准;我们只需要"够准的预算控制"不需要精确计费;启发式零依赖、可单测、离线
- 不选 B：tiktoken 装它还要下 encoding 文件,对非 OpenAI 模型是假精确
- 不选 C：数 token 还要发请求,本末倒置
- 改变条件：若某 provider 在 usage 里回 prompt_tokens,可用真实值反校准启发式系数

### D-15: L2/L3/L4 的"富化"具体喂什么
- 决策：patch(diff)是必含基底,先保证所有文件 patch 进预算;再按层级叠加富化上下文
  - L2(改动小)：每个改动文件的**整文件全文**——小 PR 全貌最有利于发现跨函数问题
  - L3(改动中)：**抽取式**——文件 import 段 + hunk 周边窗口(默认 ±40 行)+ 同文件其他函数/类签名,比全文省 token 又保留结构
  - L4(改动大)：**仅 patch**,并在上下文里显式写"跨文件引用未分析,本段为局部 review",对应误报控制原则
- 预算执行：按文件优先级(改动行多的优先富化)逐个尝试加富化块,加不下就跳过该块并记 skipped,最终在 ContextBundle 里汇报哪些被裁
- 为什么 patch 永远优先:没有 diff 就无从评审,全文/签名是"锦上添花"
- 改变条件：接入语义检索后 L3 的"同文件签名"可升级为"跨文件相关函数"

### D-13: Fetcher 输出用 dataclass 而非 Pydantic
- 决策：fetcher 的 PullRequestData / ChangedFile 用 dataclass，不用 Pydantic
- 理由：这是"从 GitHub 抓到的原始事实"，无需校验/序列化约束；Pydantic 留给 PR7 的 Finding/ReviewReport（要 JSON 序列化给前端、要置信度校验）
- 改变条件：若 fetcher 输出要直接走 API 返回给前端，再转 Pydantic

### D-24: 多模型交叉验证的范围与裁决（亮点 4）
- 目标：用异构模型(Azure GPT-4.1-mini)对高风险 finding 做"第二意见"，命中题目"模型选择设计思路"且回答"误报控制"
- 范围：只对 reasoner 已 confirmed 且 severity=high 的 finding 交叉验证。理由：
  - high 项最影响合并决策，第二意见花在刀刃上
  - Azure 配额 10k TPM 有限，不能全量验
  - low/medium 误报代价低，不值得再烧一次异构调用
- 裁决(写进 cross_check,喂给已有置信度公式 D-08)：
  - agree(都认为是真问题) -> cross_check=agree,置信分 +0.15
  - disagree(验证模型认为不成立) -> cross_check=disagree,置信分 -0.2,且严重度不再当 high 主导,UI 标注"模型有分歧"
  - 验证失败/Azure 不可用 -> cross_check=none,静默跳过,不影响主流程(降级而非崩)
- 为什么不用第三个模型投票：两个异构模型(DeepSeek 系 + OpenAI 系)已足够体现"交叉",三模型边际收益低且更慢更贵
- 可开关：CrossValidator 可注入/可禁用,Azure 没配时自动跳过,保证没有 Azure 也能完整跑
- 改变条件：配额充足可扩到 medium;要更强共识可加第三模型多数投票

### D-25: 交叉验证放在 aggregator 之前还是之后
- 决策：放在 router 产出 RawReview 之后、aggregate 之前,作为独立 CrossValidator 作用于 RawFinding
- 理由：cross_check 是置信度评分的输入信号(D-08 公式里已有该项),必须在 aggregate 打分前填好;且交叉验证针对"已确认的高风险"，正是 router 深读后的状态
- 编排：review_service 里 fetch->context->router->(cross_validate)->aggregate,交叉验证是可选中间步
- 改变条件：无

### L-01: 开发机无 gh CLI，改用 GitHub REST API 建 PR
- 现象：`gh` command not found（本地与 VM 均未装）
- 原因：环境只给了 git + GH_TOKEN，没预装 gh

### L-07: GitHub 错误直接把原始 JSON 抛给用户，体验差
- 现象：在线站点粘一个不存在的 PR，错误信息是 `GitHub API 错误 status=404: {'message': 'Not Found', 'documentation_url': ...}`
- 问题：原始 JSON 对用户不友好，评委一眼觉得"没打磨"
- 解决：加 _friendly_github_error() 把 404/403/401/422 翻译成中文友好提示，不暴露原始 JSON
- 教训1：所有面向用户的错误出口都要过一遍"人话化"，尤其是第三方 API 的原始报错；边界路径的体验也是体验分
- 教训2（更值钱）：第一版改完单测全绿就合了，但调用点的 Edit 因缩进静默失败、helper 根本没接上，线上仍是原始 JSON。根因是**单测只测了 helper 函数、没测 fetch() 调用点**。补了走真实 fetch() 路径的回归测试才真正修好。**测了零件不等于测了装配**——面向用户的行为必须测端到端出口；改完一定要在真实环境复验，不能只信单测全绿

### L-08: 净室验证发现 make install 不装 pytest，评委跑测试会卡
- 现象：全新 clone 严格照 README 走(净室验证)，make install 只装 requirements.txt(运行依赖)，评委若跑 pytest 报 No module named pytest，README 也无任何测试指引
- 问题：项目宣称 85+ 测试，但评委拿到手跑不起来，影响可信度与"使用体验"分
- 解决：加 make test(建 venv + 装 requirements-dev.txt + 跑离线单测)与 make install-dev；README 快速开始补一行；在 /tmp 净室实测 make test -> 93 passed
- 教训：自己环境早配好会掩盖"从零开始"的坑。涉及评委/用户首跑体验的，必须在干净环境(全新 clone)严格照文档走一遍，而不是在已配好的机器上验

### L-06: 缺 .dockerignore，build context 把 .venv/node_modules 发给 daemon
- 现象：docker-compose context 是仓库根(.)，COPY backend/ 还会把 __pycache__/.pytest_cache 拷进镜像
- 风险：build context 含 .venv(几百 MB)和 frontend/node_modules，传输慢；镜像里混入缓存与测试产物，不干净
- 解决：加 .dockerignore 排除 .venv/node_modules/dist/__pycache__/docs/deploy/.git 等
- 教训：用仓库根当 build context 时 .dockerignore 是必需品，否则把整个工作区(含巨型依赖目录)塞给 docker daemon

### L-05: 后台任务态 _jobs 无界增长——长跑服务内存泄漏
- 现象：review 任务态存进程内 dict，每次 review 留一条永不清理
- 风险：演示/长跑时 _jobs 无限增长，最终吃满内存
- 解决：改 OrderedDict 做有界 LRU(上限 100)，超出 popitem(last=False) 丢最旧；加 _register_job 封装+单测验证淘汰
- 教训：任何"按请求累积的进程内状态"都要想清楚回收策略，不能只 put 不 evict

### L-04: 新增交叉验证后单测从 0.9s 变 143s——测试偷偷打了真实网络
- 现象：PR12 加交叉验证后，全套单测从 0.9s 暴涨到 143s（仍 pass）
- 原因：test_cache 的 stub router 返回一个 confirmed/high 的 finding；ReviewService() 默认建真 CrossValidator(enabled=True)，于是对这条 finding 发了真实 Azure 调用 + 退避重试
- 解决：cache 相关测试构造 ReviewService 时传 enable_cross_validate=False（这些测试只测缓存，不该碰网络）
- 教训：1) 单测变慢是信号，要查不是忍；2) 引入"默认启用的外部调用"组件后，所有间接构造它的测试都可能被拖下水，要么默认禁用要么强制注入 stub；3) 用 --durations 一眼定位慢用例

### L-03: env_file 用相对路径，从 backend/ 起服务时 key 静默为空
- 现象：本机单测/smoke 全过(我 source 了 env)，但部署到 VM 从 backend/ 起 uvicorn 后所有 LLM 调用 APIConnectionError 重试 4 次失败
- 排查：VM 上 curl deepseek 200 正常 -> 不是网络；打印 settings.deepseek_api_key 长度=0 -> 是 key 没加载
- 原因：config.py 写 `env_file=".env"`，pydantic-settings 按**当前工作目录**解析相对路径；uvicorn 从 backend/ 启动，.env 在仓库根 /opt/pr-review/.env，找不到 -> key 空 -> SDK 无鉴权连接报 APIConnectionError(误导，像网络问题)
- 解决：env_file 改成基于 __file__ 的绝对路径候选列表(仓库根 + backend 目录都找)
- 教训：1) 配置文件路径永远用绝对路径(基于 __file__)，别信 cwd；2) "连接错误"未必是网络，空鉴权也会报 APIConnectionError，要先验证配置加载；3) 本机 source env 掩盖了这个 bug，必须在干净部署环境(VM)测才暴露——这正是"服务测试上 VM"约束的价值

### L-02: 本地 Python 3.10 与 BRIEF 推荐的 3.11 不一致
- 现象：`python3 --version` = 3.10.12
- 原因：基础镜像/系统自带就是 3.10
- 解决：开发用 3.10（代码不用 3.11 专属语法，如 `tomllib`/exception groups）；部署 Dockerfile pin `python:3.11-slim`，二者隔离
- 教训：写代码避开 3.11-only 特性，保证两套环境都能跑

### 5.4 AI 出过的错与修正（真实例子，体现不黑盒）
- **L-03** .env 相对路径：本地能跑，部署到 VM 后 key 静默为空，所有 LLM 调用报 APIConnectionError（伪装成网络问题）。在真实服务器上排查才定位，改绝对路径解析。
- **D-18** 去重键选错：初版按标题前缀去重，单测立刻暴露"同一问题措辞不同会漏合并"，改用文件+类别+位置。
- **L-04** 测试偷打网络：加交叉验证后全套单测从 0.9s 暴涨到 143s，发现 cache 测试间接触发了真实 Azure 调用，改为注入禁用。
- **L-05** 内存泄漏：后台任务态 dict 只 put 不 evict，代码审查发现，改有界 LRU。
- 共同点：这些都是**测试或真实环境验证**抓出来的，不是 AI 自己声称"没问题"——这正是人工把关的价值。
