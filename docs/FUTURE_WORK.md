# 未来扩展方向

> 对应题目明确要求说明的第三个设计点：**未来扩展方向**。
> 72 小时聚焦核心链路（拉取 → 分层上下文 → 多模型路由 → 置信度聚合 → 流式输出 → 交叉验证），
> 以下是已识别、但本期有意未做的扩展，按价值/可行性排序。

## 1. 语义上下文层（提升长 PR 的跨文件理解）

当前 L4（大 PR）只对改动符号做 grep 式跨文件引用。可接入 **sqlite-vec** 对仓库函数建向量索引，在 L3/L4 之间加一层"语义相似函数召回"——把"这个改动可能影响哪些地方"从字符串匹配升级为语义匹配。

未做原因：3 天内 embedding + 建库的收益不稳，分层启发式已能覆盖主要场景，且更可解释。

## 2. 私有部署 / 本地模型模式

企业不愿把私有代码发给公网 LLM。LLM 抽象层（`llm_provider.py`）已留 provider 适配点，可接入本地 **vLLM** 起的开源模型（DeepSeek-V3 / Qwen-Coder 等），走相同的 OpenAI 兼容协议。配合"本地仓库 clone 模式"（不走 GitHub API，直接读本地文件）即可完全离线评审。

## 3. PR 评论回写

当前是"读 PR → 出报告"。可加一步：把高置信 finding 以 **inline review comment** 形式写回 GitHub PR（GitHub Review API），让评审结论直接落到开发者的工作流里，而非停留在独立页面。

## 4. 增量评审持久化

当前缓存是进程内的（重启即清空）。可加 **SQLite 后端**（缓存接口已留 get/put 抽象），跨重启保留：
- 同一 PR 多次 push 的历史 review；
- 跨 PR 的风险类型统计，做**团队代码质量趋势看板**（哪类问题反复出现）。

## 5. 多语言专项规则

当前 prompt 是通用的。可针对不同语言的高频坑做定向增强：
- Go 的 nil pointer / error 忽略；
- Python 的可变默认参数 / 裸 except；
- JS 的 == vs === / 异步竞态。
以 few-shot 负例形式注入对应语言的 system prompt。

## 6. 误报率的离线评测集

当前误报控制靠 reasoner 二次核实 + 交叉验证 + 置信度分级，效果靠人工抽查。可建一个**标注好的 PR 测试集**（已知哪些是真问题、哪些是干扰），离线跑出准确的误报率/漏报率数字，用于：
- 标定置信度阈值与各信号权重；
- 回归测试 prompt 改动是否真的降低了误报。

## 7. 响应速度优化

当前 reasoner 逐条深读是串行的。在配额允许下可：
- **并发**调用 reasoner（多条候选同时深读）；
- token 级流式思维链（前端逐字显示 R1 推理），把"等待感"转成"过程感"。

---

以上扩展点都建立在当前已冻结的接口契约之上（`Finding` / `ReviewReport` / `LLMProvider` 抽象），属于增量演进，不需要推倒重来。
