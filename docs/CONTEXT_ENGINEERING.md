# 上下文获取方式（上下文工程）

> 对应题目明确要求说明的第二个设计点：**上下文获取方式**。
> 决策推导见 [复盘.md](复盘.md) D-05 / D-12 / D-14 / D-15。

## 1. 问题

PR Review 用 LLM 的核心矛盾：
- **只给 diff**：模型缺上下文，看不到被改函数的调用方/被调方，容易误报；
- **把整个仓库塞进 prompt**：爆 context window，烧钱，且大量无关代码稀释注意力。

所以上下文不是"给多少"的问题，而是"**按需分层、按预算裁剪**"的问题。

## 2. 分层策略 L1–L4

按 PR 的**改动规模**决定喂多少，受一个可配 token 预算（默认 24000）约束。

```
拿到 PR diff
   │
   ├─ L1（总是）：PR 标题/描述 + 改动文件清单 + 每文件增删行数
   │
   ├─ 改动 < 800 行  → L2：每个改动文件的完整内容
   ├─ 800 ~ 3000 行 → L3：抽取式（import + 函数/类签名 + diff hunk ±40 行窗口）
   └─ > 3000 行      → L4：仅 diff，并声明"局部 review，跨文件未分析"
   │
   ▼ 累计 token 超预算？
   ├─ 是 → 裁剪低优先内容，在报告里声明哪些没看全
   └─ 否 → 组装最终 prompt
```

| 层 | 触发 | 喂给模型的内容 | 设计意图 |
|---|---|---|---|
| L1 | 总是 | 元信息 + 文件清单 | 永远最高优先级，不可裁 |
| L2 | 改动小 | 每个改动文件**全文** | 小 PR 给全貌，最利于发现跨函数问题 |
| L3 | 改动中 | **抽取式**：import 段 + 函数/类签名 + 改动周边窗口 | 远小于全文的 token 下保留结构 |
| L4 | 改动大 | **仅 diff** + 明确声明未完整 review | 宁可诚实说没看全，不假装看全乱判 |

阈值（800 / 3000）、预算（24000）、窗口（±40 行）均可配置，是经验初值。

## 3. 两条核心原则

### 原则一：diff 永远优先
diff 是评审的基底——没有 diff 就无从评审。所以预算分配时：
1. 先按"改动行数降序"保证所有文件的 diff 进预算；
2. 富化内容（全文 / 抽取片段）是"锦上添花"，预算不足时**先砍富化**；
3. 实在不够，低优先文件的 diff 也可被裁，但**每砍一处都写进报告**。

### 原则二：超预算主动声明，绝不静默截断
当内容超预算或文件全文拉取失败时，系统在喂给模型的上下文里**显式写明**：
> "本段未完整 review / 跨文件引用未分析 / 文件 X 仅基于 diff 评审"

这直接服务于**误报与漏报控制**——模型知道自己"没看全"，就不会基于残缺上下文输出过度自信的错误结论。这比"悄悄截断后照常输出"安全得多。

## 4. token 估计：确定性启发式（D-14）

不引入 tiktoken，用自写启发式：ASCII 约 4 字符/token，CJK 约 1 字符/token，分类加权、向上取整（宁可略高估，避免超预算）。

为什么不用 tiktoken：DeepSeek 不是 OpenAI tokenizer，tiktoken 对它本就不准；我们只需要"够准的预算控制"，不需要精确计费。启发式零依赖、离线、可单测。

## 5. GitHub 数据获取的边界处理（D-12）

上下文的原料来自 GitHub，拉取层做了这些防御：
- 大 PR：文件清单分页迭代并设 `max_files` 上限，超出标 `files_truncated` 而非静默丢；
- 二进制 / 超大文件：`patch` 为 None 时保留文件条目（含增删行数），上层降级为"只看文件名"；
- 文件全文：>1MB / 目录 / 非 UTF-8 一律 catch 后返回 None，不让整次 review 崩。

## 6. 实测

- psf/requests#7487（7 行改动）→ 判为 L2 → 拉文件全文富化，整体约 9567 token，远低于 24000 预算；
- prompt 渲染包含：PR 概览 + 上下文完整性声明（如有裁剪）+ 逐文件 diff + 富化内容。

## 7. 可改之处

- 接入 sqlite-vec 做语义检索：在 L3/L4 之间加一层"跨文件相关函数召回"，把 L4 大 PR 的跨文件理解从"grep 符号"升级为"语义相似"；
- 用各 provider 真实返回的 prompt_tokens 反校准启发式系数。
