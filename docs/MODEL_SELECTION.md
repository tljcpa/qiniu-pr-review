# 模型选择设计思路

> 对应题目明确要求说明的第一个设计点：**模型选择**。
> 本文说明"在哪个阶段用哪个模型、为什么、代价与取舍"。决策推导见 [复盘.md](复盘.md) D-06 / D-16 / D-24。

## 1. 总体策略：三段式异构路由

不是"一个模型一把梭"，而是让每个模型干它最划算的活：

| 阶段 | 模型 | 职责 | 为什么是它 |
|---|---|---|---|
| 一扫 | `deepseek-chat` | 全量快扫，标出可疑片段候选 | 便宜、快，召回优先 |
| 二读 | `deepseek-reasoner` | 对每条候选逐一深读核实，保留思维链 | 强推理，精度把关；`reasoning_content` 可解释 |
| 三验 | `gpt-4.1-mini`（Azure） | 对高风险 finding 做异构第二意见 | 与 DeepSeek 系异构，交叉验证更有意义 |

```
分层上下文
   │
   ▼  deepseek-chat（全量，便宜）
候选清单 ──► 无候选 ──► 直接出总结
   │
   ▼  deepseek-reasoner（逐条深读，保留 R1 思维链）
   ├─ false_positive ──► 丢弃（误报控制主力）
   └─ confirmed / uncertain
        │
        ▼  仅 high：gpt-4.1-mini 交叉验证
        ├─ agree    ──► 置信度 +，标 [x-check ✓]
        └─ disagree ──► 降级 medium，标分歧
```

## 2. 为什么这样分

### 为什么不全程上 reasoner
reasoner 贵且慢。对一个 PR 里大量明显无风险的代码，用 reasoner 是浪费。先用便宜的 chat 高召回过滤出候选（通常个位数），再让 reasoner 只啃这几块硬骨头——成本与质量的平衡点。

### 为什么 reasoner 逐条单独调用，而不是一次批量（D-16）
`reasoning_content` 是按"整次 completion"返回的。若把多条候选塞进一次调用，多条 finding 会共享同一段思维链，无法在 UI 上逐条展开。**逐条调用 = 每条 finding 拥有独立思维链**，这是"思维链可见化"亮点的数据结构前提。代价是 N 条候选 = N 次 reasoner 调用，用 `max_deep_read`（默认 12）封顶防爆。

### 为什么交叉验证只给 high（D-24）
- high 项最影响"能不能合并"的决策，第二意见花在刀刃上；
- Azure 配额有限（10k TPM），不能全量验；
- low/medium 即使误报，代价也低，不值得再烧一次异构调用。

### 为什么用异构模型而非同模型投票
交叉验证的价值在于"不同训练背景的模型独立得出同一结论"。DeepSeek 系 + OpenAI 系是真正的异构；同一个模型投两次只是采样噪声。

## 3. 置信度如何利用模型信号（D-08）

每条 finding 的置信分（0~1）由多个模型信号加权：

| 信号 | 权重 | 含义 |
|---|---|---|
| reasoner verdict | confirmed +0.5 / uncertain +0.1 | 核实结论比初次自评更可信，故权重最大 |
| 是否经 reasoner 深读 | +0.15 | 深读过的更可信 |
| 思维链充分度 | 0~0.2（封顶） | 推理越充分越可信；封顶防"啰嗦刷分" |
| 交叉验证 | agree +0.15 / disagree −0.2 | 异构模型共识/分歧 |
| 严重度自评 | high +0.1 / medium +0.05 | 轻微加权，不主导 |

≥0.65 → high，≥0.35 → medium，否则 low（UI 默认折叠 low）。

## 4. 实测数据

对一个含明显高危 bug 的 PR（SQL 注入 / 空指针 / float 金额+无事务）实测：

- chat 扫出 6 条候选 → reasoner 丢弃 2 条误报 → 保留 4 条；
- 3 条 high 全部经 gpt-4.1-mini 交叉验证 `agree`，置信度 1.0，附第二意见说明；
- 单次约 17.6 万 token（深读 + 交叉验证），响应数十秒级。

对一个真实正确的修复 PR（psf/requests#7487）实测：

- chat 扫出 1 条候选 → reasoner 判为误报丢弃 → 最终 0 条——**对正确代码不硬报**，体现误报控制。

## 5. 鲁棒性

- 任一模型调用失败：限流/超时/连接错误指数退避重试；不可重试错误立即降级。
- Azure 未配置或交叉验证失败：静默跳过，不影响主流程——**没有 Azure 也能完整跑**。
- 模型返回非 JSON：容错解析（剥 ```json``` 包裹 / 正则抠 `{}`），失败则该条标 uncertain 而非整次崩溃。

## 6. 可改之处（约束条件）

- 配额充足时可把交叉验证扩到 medium；
- 要更强共识可加第三模型多数投票；
- 要 token 级实时思维链（逐字蹦）需把 reasoner 调用改 async streaming。
