# 答辩材料（5 分钟脚本 + Demo 分镜 + Q&A 预案）

> 既是现场答辩脚本，也是录 Demo 视频的台本。
> 时间分配按 BRIEF §8：问题陈述 / 模型选择 / 上下文工程 / 误报控制 / 现场 demo。
> 台词是草稿，wly 用自己的话讲即可，关键是把"为什么"讲清。

---

## 0. 一句话定位（开场前心里有数）

"用户给一个 GitHub PR 链接，系统自动拉变更、用大模型分析，输出**总结 / 风险 / 建议**；
我们的差异化是把 AI 的**推理过程摊开给人看**，并用**多模型协作 + 分层上下文**控制误报。"

---

## 1. 问题陈述（0:00 – 0:30，30 秒）

> "代码评审里用 AI，三个真实痛点：
> 一是 **PR 太长**，上下文塞不进模型，硬塞就截断、输出错结论；
> 二是 **误报多**，AI 动不动报一堆，把真问题淹没，评审反而更累；
> 三是 **黑盒**，AI 给个结论但不说为什么，评审不敢信。
> 我们这套工具就是针对这三点设计的。"

---

## 2. 模型选择策略（0:30 – 1:30，60 秒）

> "我们不是用一个模型一把梭，而是**三段式异构路由**，让每个模型干最划算的活：
> - 第一遍用便宜快的 **deepseek-chat** 全量快扫，高召回标出可疑片段；
> - 第二遍用 **deepseek-reasoner** 对每条候选逐一深读核实——注意是**逐条单独调**，
>   这样每条问题都有一段**独立的思维链**，能在界面上单独展开；
> - 第三遍对**高风险**问题，再用 **GPT-4.1-mini** 这个异构模型做独立第二意见，
>   两个模型都认是真问题，置信度才拉满；有分歧就降级、标出来。
> 这直接回答了题目要的'模型选择设计思路'——便宜的做召回，强的做精度，异构的做交叉验证。"

**截图/演示点**：展开一条 finding 的 reasoning_content 思维链；指出 `[x-check ✓]` 交叉验证徽章。

---

## 3. 上下文工程（1:30 – 2:30，60 秒）

> "长 PR 怎么喂给模型？我们做**分层上下文 L1 到 L4**：
> - 小改动给整文件全文；
> - 中等改动给抽取式——import、函数签名、改动周边窗口，省 token 又保留结构；
> - 大改动只给 diff，并且**主动在上下文里声明'这段我没看全、跨文件没分析'**。
> 最后一点是关键：**宁可诚实说没看全，也不假装看全然后乱判**——这本身就是误报控制的一部分。
> 整个过程受一个 token 预算约束，diff 永远优先保证，富化内容预算不够先砍，每砍一处都告诉用户。"

**截图/演示点**：进度流里的 `context L2 · 9567 tok`；解释大 PR 会显示截断声明。

---

## 4. 误报控制（2:30 – 3:30，60 秒）

> "误报控制贯穿整条链路：
> - reasoner 深读阶段以**怀疑论者**的姿态复核，判定是误报的**直接丢弃**；
> - 每条留下的问题打一个**置信度分**，信号包括：reasoner 是否确认、思维链是否充分、交叉验证是否同意；
> - 界面上**低置信默认折叠**，高置信突出，不让低质量猜测淹没真问题。
> 举个真实例子——我们拿一个**已经合并的正确修复 PR** 测试，chat 扫出 1 个疑似问题，
> reasoner 深读后判定它其实是正确处理、是误报，最终**一条都不报**。对好代码不硬挑刺，这很重要。"

**截图/演示点**：对正确 PR 的"无风险"结果；对比 demo PR 的高危结果与置信度标注。

## 6. 可能被问到的问题（预案）

**Q：如果 LLM 把好代码标成风险怎么办？**
A：三道闸——reasoner 二次复核直接丢误报、置信度分级折叠低置信、高风险交叉验证。实测对正确 PR 能做到 0 误报。

**Q：大公司不会把私有代码发给公网 LLM，怎么解决？**
A：我们的 LLM 抽象层是 provider 无关的，留了适配点，可接本地 vLLM 起的开源模型；配合本地仓库读取模式即可完全离线。已列入扩展方向。

**Q：为什么自己写而不用 LangChain？**
A：核心链路（拉取/分层/路由/聚合）就几百行，自己写能精确控制 token 预算和思维链透出，也不被框架黑盒绑架。这是刻意的工程选择。

**Q：成本/速度？**
A：小 PR 约 20 多秒、2 万 token 量级；用便宜模型做召回、强模型只深读候选来平衡。同一 PR 二次看走缓存秒回。

**Q：思维链可见有什么实际价值？**
A：评审最大的顾虑是"AI 凭什么这么说"。把 reasoner 的推理摊开，评审能快速判断这条值不值得信，而不是盲信或全盘否定——可解释性直接转化为可用性。

**Q：和现成的 GitHub Copilot / CodeRabbit 比？**
A：我们的差异在三点——思维链对用户可见、多模型交叉验证给置信度、分层上下文+主动声明截断。重点不是功能多，是**让结论可信、可解释**。

- 痛点：长 / 误报多 / 黑盒

- Demo：PR #14，进度流 → 高危 → 思维链 → x-check → 折叠
